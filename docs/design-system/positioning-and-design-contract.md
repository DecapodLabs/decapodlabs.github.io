# Decapod Labs positioning and design contract

## The lab and its flagship

Decapod Labs builds infrastructure for autonomous engineering. The research thesis is that agents can carry useful work across ordinary failures when they can check their own understanding, recover project knowledge, and consult the authority granted for the work. Decapod puts that thesis into practice as the governance kernel existing coding agents call. The person delegates the desired outcome. The agent investigates, implements, validates, and delivers under the repository’s policy. Decapod provides the project context, custody, and evidence the agent needs for that work.

Give first-time readers enough information to apply the idea. Explain what the agent knows, how work is owned, what persists between sessions, which decisions can be made within standing authority, and when a human decision is needed. Use substantial examples from engineering and research.

## Homepage reading sequence

1. **Purpose and entry.** Introduce the lab and the product in plain language. Show the Local installation path for someone ready to begin.
2. **Ordinary work.** Explain how an existing coding agent receives an outcome, resolves relevant project knowledge and constraints, and coordinates execution. Show an ordinary feature request and the recovery from a test failure. Identify these examples as illustrations of the workflow.
3. **Capabilities.** Explain the Constitution’s curated defaults, project-specific specifications, context capsules, durable decisions, custody, workspaces, recovery, and validation. Keep the fourteen capability explanations visible with direct links into the manual.
4. **Research and applications.** Explain the question and contribution of Accountable Agentic Execution, with pre-results status in publication metadata. Show Waystead’s interdependent game systems, the kernel film, and the founder’s Rework letter.
5. **Case study.** Provide a contextual route to the exact recorded authorization change. Leave the dated receipt, recordings, independent negative controls, and edge cases in the evaluation.
6. **Start or select Cloud.** Explain ordinary Local use and distinguish configured, admitted Cloud work from administrative provisioning and purchases.

The reader can reach privacy and evaluation references directly from the footer. Historical publication records remain attached to their actual client versions, source, and outcome.

| Join a configured team | Clone and describe the desired change. The administrator establishes scoped authority and capacity | The released client exercises supported repository authorization. | Understand an evaluation | Follow the result or architecture link into the technical case study | Read the question, mechanism, observed behavior, and evidence attached to the specific run | The reader can distinguish applied behavior, verification, and publication |
| Research | Read the report or browse its source and harness | Follow the definitions, research question, and reproducibility method | Pre-results technical report with public methods |

The outcome view should identify the original request, accepted changes, result location, relevant evidence, and any remaining dependency. The repository and forge authorize publication.
